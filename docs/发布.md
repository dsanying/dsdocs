# 发布流程

项目通过 GitHub 源码仓库分发；正式版本可使用签名标签和 GitHub Release 记录变更、兼容范围、部署步骤及已知限制。需要容器分发时另构建 reader/management 两个目标并发布对应镜像摘要。源码提交不等于正式发布。

开发、本地验证、CI 与生产在同一提交使用同一依赖声明及锁文件，不按环境另存版本文件。运行依赖只声明一次；生产构建不得现场解析另一套版本。包的 peer 范围声明兼容边界，宿主的精确依赖及锁文件决定实际安装版本。

发布前执行 pnpm check、pnpm test:browser、pnpm test:settings:browser、pnpm test:containers、pnpm audit:all，复核账号权限、子路径、草稿隔离、恢复备份及镜像运行。第三方许可证由依赖锁文件收集，项目 MIT 不替代第三方许可义务。

未完成的验收不得写成已通过。正式发布必须由维护者明确授权；源码提交、npm 包和 GitHub Release 分别核验，不以其中一项成功代替其他项。

## React 集成包

`packages/react` 通过个人账号的公开 scope 发布为 `@dsanying/dsdocs`，根项目及两端应用保持 private。`/editor`、`/reader`、`/style.css`、`/locales/zh-CN` 是公共入口；应用通过同一包消费这些组件，禁止复制编辑器实现。宿主负责认证、授权、存储、发布事务和附件策略，组件包不启动额外服务、不接管宿主账号。

版本遵循语义化版本。补丁修复不改变公共契约，新增可选能力使用 minor，不兼容变更使用 major；0.x 阶段不兼容变更至少提高 minor，并提供迁移说明。宿主固定明确版本及锁文件，升级时运行编辑往返、上传、草稿隔离、发布、历史、权限与读者回归。组件升级需要宿主构建；正文发布只修改持久化内容，无需构建或重启。

发布顺序：

1. 在干净分支完成上列门禁，以及 `pnpm check:package`；检查包清单仅包含 dist、README、LICENSE、THIRD_PARTY_NOTICES.md、package.json，保留依赖许可证。
2. 本地 `git commit -S` 签名提交，通过评审及主分支检查后，以对应提交创建签名标签 `v<version>`；标签版本必须与包版本一致。
3. 执行 `pnpm -C packages/react pack --out /绝对路径/dsdocs-<version>.tgz`，在隔离宿主安装该归档，验证公开入口与类型。保存归档 SHA-256，GitHub Release 附上同一归档、校验和、升级说明与实际验收结果。
4. `npm whoami` 核对发布者为 dsanying，执行 `npm publish /绝对路径/dsdocs-<version>.tgz --access public`，由维护者完成所需双因素认证。不将登录令牌写入仓库或工作流。
5. 从公共 registry 查询版本、完整性和公开访问，重新安装正式版本验证。发布的版本不可覆盖；修复提高版本后重新走流程。`npm deprecate` 仅用于明确标记故障版本，宿主回退锁定上一已验证版本；程序回退不能覆盖业务数据。

`pnpm test:containers` 会先从当前源码构建两端本地镜像，再启动隔离卷执行测试，避免把旧镜像结果当成本次源码验证；不会推送镜像。
