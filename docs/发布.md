# 发布与部署

仓库公开、软件版本发布和站点部署是三个动作。公开源码不等于发布稳定版本；GitHub Release 不会自动启动服务，也不包含用户文档和账号。

## 版本分发

首版按独立应用分发：

| 产物                          | 用途                                       |
| ----------------------------- | ------------------------------------------ |
| Git 签名标签和 GitHub Release | 固定可追溯版本、变更说明和下载入口         |
| 源码归档及 SHA256SUMS         | 从锁文件安装并构建                         |
| 容器镜像                      | 运行内容服务与管理端，数据库单独持久化     |
| 静态读者端构建产物            | 部署在静态服务器上，示例产物只包含通用示例 |

当前项目不是发布到 npm 的可安装库，各应用保留 `private: true`，防止误发包。后续若提供 CLI 或独立 SDK，再设计对应的包和兼容承诺。

## 发布前准备

先完成审核、测试、依赖检查和文档核对，再签名提交。工作区干净时运行：

```sh
pnpm release:prepare
```

命令执行完整检查、三套生产依赖审计、本地容器构建和容器账号烟测，然后生成源码归档、示例静态站点归档、校验和及固定提交记录。输出默认在已忽略的 `release-artifacts/<commit>`，可用 `DSDOCS_RELEASE_OUTPUT` 指定仓库外路径。需要空闲的本地 14320 端口和可用 Docker。浏览器依赖按维护手册安装。

准备流程只创建本地 `dsdocs:preflight` 镜像，不创建标签、Release，不上传镜像或部署。GitHub 的 `prepare-release` 工作流也只执行构建并上传工作流产物，不发布正式版本。

## 正式发布

确认固定提交的检查和发布准备全部成功后，由维护者创建签名版本标签，例如 `v0.1.0`，再创建对应 GitHub Release，附变更说明、归档与校验和。容器可发布到 GitHub Container Registry，使用版本标签并记录不可变镜像摘要。首版应明确实验阶段的编辑器和当前支持边界。

未获发布指令前，不执行标签推送、Release 创建或镜像上传。现有工作流没有这些写入步骤。

## 内容服务部署

```sh
docker compose build
# 初始化前，在当前进程设置 DSDOCS_ADMIN_USERNAME 和 DSDOCS_ADMIN_PASSWORD。
docker compose run --rm -e DSDOCS_ADMIN_USERNAME -e DSDOCS_ADMIN_PASSWORD backend \
  node node_modules/tsx/dist/cli.mjs scripts/init.ts
docker compose up -d
```

构建时设置目标 `DSDOCS_BASE_PATH`，运行时设置浏览器实际 `DSDOCS_ORIGIN`。反向代理保留完整子路径，不剥掉 `/docs`。数据库卷只给一个内容服务实例使用；数据库、会话和上传内容不进入镜像。初始化成功后从运行环境移除初始化口令变量。

使用独立静态前台时，将 `/docs/admin`、`/docs/api`、`/docs/preview` 路由到内容服务，其余 `/docs` 路由到静态产物。后台中断不会影响已经部署的静态文件。导出和构建失败时保留上一个完整静态产物，不覆盖为半成品。

## 升级、备份与回退

升级前备份数据库，先在副本中验证迁移与内容构建。运行程序会拒绝高于自身支持版本的数据库，不通过删除数据库来“回退”。存在结构升级时，回退旧镜像须同时恢复对应的备份。

静态站点采用完整目录替换，可回退到上一个构建产物。下线或删除后台文档不会撤回已经导出的文件，必须重新导出和部署。已发布文件导出不含草稿、用户或历史，数据库备份需要独立执行。
